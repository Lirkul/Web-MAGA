# Контекст проекта для Codex — Web-MAGA

> Прочитай этот файл перед каждым заданием. Это постоянная спецификация лабораторной работы. **Не реализуй весь проект автоматически:** выполняй только очередную задачу, явно указанную пользователем в текущем сообщении.

## 1. Проект и требования преподавателя

**Название:** «Система управления библиотечным фондом», вариант 1.
**Репозиторий:** https://github.com/Lirkul/Web-MAGA.git.
**Тип:** серверное REST API на Node.js. **Фронтенд не нужен:** никаких React, Vue, страниц сайта, SPA и т. п. Взаимодействие — через Postman/curl и Swagger UI.

Предметная область: каталог книг, читатели, выдача и возврат книг.

Специфические требования лабораторной:
1. Рассчитывать просрочки и штраф за возврат книги позже установленного срока; раз в сутки запускать cron-задачу, обновляющую статусы просроченных невозвращённых выдач.
2. Предоставить эндпоинты статистики: топ-5 самых читаемых книг за период и читатели с просрочками.
3. Реализовать импорт каталога из CSV с **настоящим потоковым чтением (Node.js streams)**, не загружая весь файл в память.

**Порядок сдачи:** GitHub/GitLab с осмысленной историей коммитов; `README.md` с описанием, запуском через `docker-compose up`, списком API и переменных окружения; Swagger по `/docs` при локальном запуске; демонстрация через Postman/curl и ответы на вопросы о коде и архитектуре.

## 2. Технологический стек

- Node.js LTS, JavaScript (ES Modules), Express.
- PostgreSQL 16, драйвер `pg`, параметризованный SQL, **без ORM**.
- Dockerfile, `docker-compose.yml` с сервисами `api` и `db`, healthcheck БД, постоянный том PostgreSQL; конечное приложение запускается с нуля через `docker compose up --build` (в README объяснить эквивалентную команду `docker-compose up --build`).
- `zod` для проверки входных данных, единый обработчик ошибок.
- `node-cron` для ежедневной задачи; ручной запуск той же бизнес-функции через npm-скрипт.
- `busboy` + `csv-parse` для потокового импорта multipart CSV, с ограничением размера загрузки.
- `swagger-ui-express` + файл OpenAPI 3, документация `/docs`.
- `vitest` + `supertest` для автоматических тестов; тестовые данные должны быть изолированы от основной БД.
- Нет авторизации, ролей, Redis, микросервисов и платёжных интеграций.

Код должен быть понятным для защиты студентом: простая слоистая архитектура (routes → services → repositories → PostgreSQL), явные SQL-запросы, логичные имена, без избыточных абстракций.

## 3. Предметная модель

### Book
- `id` — первичный ключ.
- `title` — обязательное название.
- `authors` — непустой массив авторов.
- `isbn` — обязательный уникальный ISBN.
- `publication_year` — год издания.
- `genre` — жанр.
- `total_copies` — общее количество экземпляров, целое неотрицательное.
- `created_at`, `updated_at`.
- В API возвращать `availableCopies = totalCopies - число невозвращённых выдач`. Не хранить это число как изменяемую копию в БД.

### Reader
- `id` — первичный ключ.
- `full_name` — ФИО.
- `email` — корректный, уникальный.
- `registration_number` — уникальный номер читателя.
- `status` — `active` или `blocked`.
- `created_at`, `updated_at`.

### Loan
- `id` — первичный ключ.
- `book_id`, `reader_id` — внешние ключи.
- `loaned_at` — фактическое время выдачи.
- `due_date` — плановая календарная дата возврата, в UTC.
- `returned_at` — фактическое время возврата, NULL до возврата.
- `status` — `active`, `overdue`, `returned`.
- `fine_amount` — начисленный штраф, рубли, по умолчанию 0.
- `created_at`.

Создать ограничения и индексы. Не удалять книгу/читателя, если по нему существует история выдач (409). Историю выдач не удалять.

## 4. Бизнес-правила

1. Выдача доступна только активному читателю и при наличии свободных экземпляров.
2. Срок по умолчанию **14 календарных дней** от даты выдачи в UTC. Клиент может передать `dueDate` (формат `YYYY-MM-DD`), но он должен быть позже даты выдачи.
3. Создание выдачи выполнять в транзакции с `SELECT ... FOR UPDATE` для строки книги: два одновременных запроса не могут выдать один и тот же последний экземпляр.
4. Возврат разрешён один раз; повторная операция → 409. Ставить `returned_at`, `status=returned` и вычислять `fine_amount`.
5. Просроченной считается **невозвращённая** выдача, у которой `due_date` строго меньше текущей календарной даты UTC. Штраф при возврате: количество полных просроченных *календарных дней* × **10 руб.** (ставка из `FINE_PER_DAY`). Пример: срок 10 ноября, возврат 12 ноября → 20 руб. Срок и сумма не могут быть отрицательными.
6. Cron раз в сутки в **00:05 UTC** (`CRON_SCHEDULE="5 0 * * *"`) переводит невозвращённые просрочки из `active` в `overdue`, не меняет возвращённые и допускает повторный запуск. Ручная команда `npm run overdue:check` вызывает ту же сервисную функцию.
7. Топ-5 самых читаемых книг — количество **выдач, оформленных** за период `from`–`to` включительно, включая возвращённые; сортировать по числу выдач по убыванию, при равенстве — по названию.
8. Список читателей с просрочками — читатели с текущими невозвращёнными просроченными выдачами, книги и количество дней; определять просрочку по датам, даже если cron ещё не сработал.
9. Уменьшать `total_copies` ниже количества невозвращённых выдач нельзя (409).
10. При импорте CSV существующие ISBN пропускать; уже существующие книги не перезаписывать.

## 5. Контракт API

Префикс API — `/api`, формат данных JSON, поля в ответе и запросах — `camelCase`. Для списков предусмотреть пагинацию `page`, `limit`, при необходимости поиск и фильтры.

**Книги:**
- `POST /api/books` — создать (201).
- `GET /api/books` — список, фильтры `search`, `genre`, `page`, `limit`.
- `GET /api/books/:id` — подробности.
- `PATCH /api/books/:id` — изменить.
- `DELETE /api/books/:id` — удалить, если нет истории выдач (204, иначе 409).

**Читатели:**
- `POST /api/readers` — зарегистрировать (201).
- `GET /api/readers` — список, `search`, `status`, `page`, `limit`.
- `GET /api/readers/:id` — подробности.
- `PATCH /api/readers/:id` — изменить или заблокировать.
- `DELETE /api/readers/:id` — удалить без истории выдач (204, иначе 409).

**Выдачи:**
- `POST /api/loans` — выдать книгу, `{ "bookId": 1, "readerId": 1, "dueDate": "2026-11-24" }`; `dueDate` необязателен (201).
- `GET /api/loans` — список, фильтры `readerId`, `bookId`, `status`, `page`, `limit`.
- `GET /api/loans/:id` — подробности.
- `POST /api/loans/:id/return` — возврат, штраф и новый статус.

**Статистика:**
- `GET /api/statistics/top-books?from=2026-11-01&to=2026-11-30` — до 5 книг и число выдач.
- `GET /api/statistics/overdue-readers` — читатели с невозвращёнными просрочками.

**Импорт:**
- `POST /api/books/import` — multipart/form-data, поле `file`, CSV UTF-8 (допустить BOM), заголовок строго `title,authors,isbn,publicationYear,genre,totalCopies`, несколько авторов в одной ячейке разделять `|`.
- Действительно парсить поток, контролировать backpressure; проверять каждую запись, валидные сохранять, плохие и дубликаты пропускать. Не читать/копить полный CSV в память.
- Пример ответа: `{ "processed": 100, "imported": 92, "skipped": 8, "errors": [{ "line": 7, "reason": "Некорректный ISBN" }] }`.
- Ошибки CSV, неверные заголовки, пустой файл, ограничение размера, ограниченный перечень ошибок в ответе, точные счётчики. Пример `samples/books.csv`.

**Сервис:**
- `GET /api/health` — 200 при здоровом приложении и соединении с БД, 503 при недоступной БД (на раннем этапе каркаса без БД допустим временный 200 со статусом приложения; позже доработать).
- Swagger UI `GET /docs`.

Ошибки — единый формат, например `{ "error": { "code": "BOOK_NOT_AVAILABLE", "message": "Нет доступных экземпляров", "details": [] } }`; корректные 400/422, 404, 409, 500. В production не отдавать стек и SQL-ошибки.

## 6. Переменные окружения

`PORT=3000`, `DATABASE_URL`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `DEFAULT_LOAN_DAYS=14`, `FINE_PER_DAY=10`, `CRON_SCHEDULE=5 0 * * *`, `TZ=UTC`.

Секреты и `.env` не коммитить; создать `.env.example` с демонстрационными значениями (без настоящих паролей). Внутри Docker Compose приложение обращается к хосту БД `db`, а не `localhost`. Миграции применяются автоматически при запуске `api` после готовности БД и повторно безопасны.

## 8. Проверки и защита

Должны быть тесты или воспроизводимые проверки: CRUD и валидация; конкурирующие выдачи последнего экземпляра; отсутствие выдачи заблокированному; возврат в срок и с просрочкой; двойной возврат; идемпотентный cron; топ-5 с периодом; просроченные читатели; CSV с ошибками и дубликатами; `/docs`, `/api/health`.

Скрипты в конечном проекте: `npm run dev`, `npm start`, `npm test`, `npm run db:migrate`, `npm run db:seed`, `npm run overdue:check`. `db:seed` должен быть повторяемым и не создавать дубликатов. README на русском содержит команды `docker compose up --build` / `docker-compose up --build`, переменные, эндпоинты, проверки curl и сценарий защиты.

## 9. ОБЯЗАТЕЛЬНЫЙ рабочий процесс Codex

**Выполняй только ОДНО задание, данное пользователем в текущем сообщении.** Не переходи к следующему этапу, даже если осталось время или контекст проекта позволяет. Этот файл определяет общие требования, а не команду реализовать всё сразу.

При выполнении каждого задания:
1. Проверь `git status`, активную ветку и `git remote -v`. `origin` должен указывать на `https://github.com/Lirkul/Web-MAGA.git` (возможен эквивалентный SSH URL). Не трогай чужие/незакоммиченные изменения и не запускай деструктивные команды.
2. Прочитай нужные части текущего кода и выполни **только запрошенное изменение**. Не создавай задел на ещё не выданные этапы.
3. Добавь необходимую для этого изменения проверку/тест. Реально выполни доступные проверки и исправь выявленные ошибки.
4. Просмотри `git diff` и включи в коммит только файлы своей задачи, без `.env`, ключей, `node_modules`, логов и данных БД.
5. Создай **ровно один осмысленный коммит** для текущего задания. Сообщение — **по-русски**, конкретное действие (например, `Добавить каркас Express и проверку состояния сервера`). Не фальсифицируй даты коммитов и не переписывай историю.
6. Выполни **`git push`** в `origin` на текущую ветку. Никогда не используй `push --force`, `reset --hard` и не создавай другую ветку без необходимости. Если нет доступа/авторизации к GitHub — чётко сообщи, что push не выполнен; не заявляй об успехе.
7. Остановись. Сообщи: что реализовано; какие команды проверки **фактически** прошли; хеш и сообщение коммита; ветку и результат push; что осталось по этому этапу. **Не выполняй следующую задачу сам.**

Не добавляй искусственные задержки между коммитами. Нормальная история — отражение реальных самостоятельных заданий, а не специально подогнанные интервалы.
