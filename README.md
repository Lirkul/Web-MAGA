# Система управления библиотечным фондом

Серверное REST API на Node.js и Express. Реализованы каталог книг, управление читателями, выдача книг, SQL-миграции и проверка состояния приложения и БД.

## Запуск через Docker Compose

Нужен работающий Docker Engine с Docker Compose. Из корня проекта выполните:

```sh
docker compose up --build -d
docker compose ps
curl -i http://localhost:3000/api/health
```

Для запуска с выводом логов используйте `docker compose up --build`. Эквивалентная команда старой версии Compose — `docker-compose up --build`.

Compose запускает `db` (PostgreSQL 16) и `api`. API ожидает успешного healthcheck БД, выполняет `npm run db` и только после успешных миграций запускает Express. При ошибке миграций сервер не стартует, контейнер завершается с ошибкой и перезапускается согласно политике Compose. Подключение к БД идёт по имени `db`. Данные сохраняются в томе `postgres_data` между перезапусками. Остановка: `docker compose down` (без удаления тома).

Демонстрационные настройки работают без `.env`. Для изменения настроек скопируйте `.env.example` в `.env`. Не используйте демонстрационный пароль для реальных данных. При изменении пароля в `.env` учитывайте: PostgreSQL применяет начальные настройки только к пустому тому.

## Локальный запуск

Нужны Node.js 24 LTS и доступная PostgreSQL 16. Можно запустить только БД командой `docker compose up -d db`, затем:

```sh
cp .env.example .env
npm ci
npm run db
npm start
```

В PowerShell файл копируется командой `Copy-Item .env.example .env`. Если выполнение `npm.ps1` запрещено, используйте `npm.cmd` вместо `npm`.

`npm start` и `npm run dev` читают `.env` штатными средствами Node.js. Уже заданные переменные окружения имеют приоритет. `npm run dev` включает штатный режим `node --watch`. Перед локальным запуском остановите контейнер API командой `docker compose stop api`, чтобы освободить порт 3000.

| Переменная | Демонстрационное значение | Назначение |
| --- | --- | --- |
| `PORT` | `3000` | Порт локального сервера; в Compose — внешний порт API |
| `DATABASE_URL` | `postgresql://web_maga:demo_password@localhost:5432/web_maga` | Подключение локального приложения к БД |
| `POSTGRES_DB` | `web_maga` | Имя БД в Compose |
| `POSTGRES_USER` | `web_maga` | Пользователь БД в Compose |
| `POSTGRES_PASSWORD` | `demo_password` | Демонстрационный пароль БД в Compose |
| `FINE_PER_DAY` | `10` | Рубли за календарный день просрочки при возврате |
| `CRON_SCHEDULE` | `5 0 * * *` | Ежедневная проверка просрочек в 00:05 UTC |

В контейнере API `DATABASE_URL` формируется из `POSTGRES_*` с хостом `db`, независимо от локального `DATABASE_URL`. Для специальных символов в имени пользователя или пароле требуется URL-кодирование в строке подключения. Порт БД 5432 опубликован только на `127.0.0.1` для локального запуска приложения.

## Схема БД и миграции

SQL-файлы находятся в `src/db/migrations/`, имена имеют формат `001_initial_schema.sql` (три цифры, затем название в нижнем регистре). Новые изменения схемы добавляйте следующим файлом; уже применённые файлы не редактируйте.

Команда `npm run db` (или `npm run db:migrate`) находит файлы по номеру и пропускает записанные в `schema_migrations`. Каждый новый файл и запись о его применении выполняются в одной транзакции. Ошибка откатывает текущую миграцию и останавливает выполнение; ранее применённые миграции сохраняются. Соединение и пул закрываются при успехе и при ошибке. Сеансовая advisory-блокировка не даёт двум процессам одновременно применять миграции одной БД.

В Docker миграции выполняются автоматически при каждом старте API. Ручной запуск в работающем контейнере:

```sh
docker compose exec api npm run db
```

Таблицы: `books`, `readers`, `loans`; служебная таблица — `schema_migrations`. Доступные экземпляры отдельно не хранятся. Уникальны ISBN, регистрационный номер и `lower(email)`. Внешние ключи выдач запрещают удаление книги или читателя с историей (`ON DELETE RESTRICT`). Ограничения проверяют обязательные поля, непустой массив авторов, статусы, неотрицательные число экземпляров и штраф.

Индексы выдач: `loans_book_id_idx`, `loans_reader_id_idx`, `loans_unreturned_due_date_idx` (только невозвращённые), `loans_loaned_at_idx`. Для ключей и уникальных ограничений PostgreSQL также создаёт индексы.

## Проверки миграций

Интеграционные тесты Vitest используют только явно заданную `TEST_DATABASE_URL` с именем БД, оканчивающимся на `_test`. Создайте отдельную пустую тестовую БД, например с демонстрационными настройками Compose:

```sh
docker compose exec db createdb -U web_maga web_maga_test
```

PowerShell:

```powershell
$env:TEST_DATABASE_URL = 'postgresql://web_maga:demo_password@localhost:5432/web_maga_test'
npm.cmd test
```

Bash:

```sh
TEST_DATABASE_URL=postgresql://web_maga:demo_password@localhost:5432/web_maga_test npm test
```

Повторно создавать тестовую БД перед каждым запуском не нужно. Тесты создают собственные временные схемы и удаляют их после выполнения; основная БД и её данные не затрагиваются. Проверяются типы, ограничения, индексы, повторный и конкурентный запуск, откат ошибочной миграции и завершение CLI. Демонстрационные строки в тестах существуют только внутри тестовой БД.

## Ошибки и валидация запросов

Ошибки API имеют формат `{"error":{"code":"NOT_FOUND","message":"Эндпоинт не найден","details":[]}}`. Некорректные данные и JSON возвращают HTTP 400, неизвестный маршрут — 404, явный конфликт данных — 409. Непредвиденные ошибки возвращают HTTP 500 с общим сообщением без стека, SQL и внутренних деталей, независимо от режима приложения.

Класс `ApiError` принимает статус, машинный код, сообщение и необязательный массив деталей. Методы `badRequest`, `notFound`, `conflict` создают типовые ошибки. Все ошибки обрабатывает `src/middlewares/errorHandler.js` после маршрутов и обработчика неизвестного пути.

Middleware `validate(schema, source)` принимает Zod-схему и источник `body` (по умолчанию), `params` или `query`. При успехе результат находится в `req.validated[source]`, включая преобразования и значения по умолчанию. Исходные `req.body`, `req.params`, `req.query` не перезаписываются. Несколько middleware можно последовательно применять к разным источникам.

Ошибки проверки возвращаются с кодом `VALIDATION_ERROR`, сообщением «Некорректные данные запроса» и деталями `{path, message}` для каждого неверного поля. Вложенные пути записываются через точку, например `contacts.0.email`. Схемы книг находятся в `src/schemas/books.schemas.js`.

`npm test` запускает тесты Vitest/Supertest: middleware проверяются с подменой БД, а API книг, читателей, выдач и миграции — с настоящей PostgreSQL по `TEST_DATABASE_URL`. Тесты сущностей создают отдельную временную схему на каждый тест и удаляют её после выполнения. Вспомогательные маршруты ошибок существуют только в тестовом приложении. Проверка `/api/health` сохраняет отдельные ответы 200/503, описанные ниже.

## API книг

| Метод и путь | Результат |
| --- | --- |
| `POST /api/books` | Создание книги, HTTP 201 и объект книги |
| `GET /api/books` | Список с поиском, фильтром и пагинацией |
| `GET /api/books/:id` | Книга по ID, HTTP 200; отсутствующая книга — 404 `BOOK_NOT_FOUND` |
| `PATCH /api/books/:id` | Частичное изменение книги, HTTP 200 и актуальный объект |
| `DELETE /api/books/:id` | Удаление книги без истории выдач, HTTP 204 без тела |

Пример создания (Bash):

```sh
curl -X POST http://localhost:3000/api/books \
  -H 'Content-Type: application/json' \
  -d '{"title":"Чистый код","authors":["Роберт Мартин"],"isbn":"9780132350884","publicationYear":2008,"genre":"Программирование","totalCopies":5}'
```

Название, непустой массив непустых авторов и ISBN обязательны. ISBN-10/ISBN-13 проверяется по формату и контрольной цифре; дефисы и пробелы удаляются, `x` приводится к `X`. Повторный нормализованный ISBN возвращает 409 `BOOK_ALREADY_EXISTS`. Строки очищаются от пробелов по краям, повторные пробельные символы заменяются одним пробелом. Неизвестные поля тела и query отклоняются с HTTP 400.

`publicationYear` — необязательное положительное целое число не позже следующего года UTC; `genre` — необязательная строка. `totalCopies` по умолчанию 0, допустимо целое число от 0 до 2147483647 (тип INTEGER в PostgreSQL). Книга возвращается с camelCase-полями, включая `createdAt`, `updatedAt` и вычисляемое `availableCopies`.

```sh
curl --get http://localhost:3000/api/books \
  --data-urlencode 'search=код' \
  --data-urlencode 'genre=Программирование' \
  --data-urlencode 'page=1' --data-urlencode 'limit=10'
curl http://localhost:3000/api/books/1
```

`search` ищет подстроку в названии, любом авторе или ISBN без учёта регистра; ISBN можно искать с разделителями. `%` и `_` считаются буквальными символами. `genre` сравнивается целиком без учёта регистра. Фильтры применяются совместно. `page` по умолчанию 1, `limit` — 10 (максимум 100); сортировка по ID по возрастанию. Ответ списка: `{data: [...], pagination: {page, limit, total, totalPages}}`. При отсутствии совпадений возвращаются `data: []`, `total: 0`, `totalPages: 0`; за пределами последней страницы `total` сохраняет общее число совпадений.

Фильтрация, подсчёт, LIMIT/OFFSET и расчёт `availableCopies` выполняются в SQL. Доступные экземпляры — `totalCopies` минус число выдач с `returned_at IS NULL`, включая `active` и `overdue`. Для всего списка выполняются два SQL-запроса независимо от количества книг.

### Редактирование и удаление

```sh
curl -X PATCH http://localhost:3000/api/books/1 \
  -H 'Content-Type: application/json' \
  -d '{"title":"Новое название","totalCopies":3,"genre":null}'
curl -X DELETE http://localhost:3000/api/books/1
```

PATCH принимает только `title`, `authors`, `isbn`, `publicationYear`, `genre`, `totalCopies`. Непереданные поля сохраняются, включая количество экземпляров: значение по умолчанию 0 применяется только при POST. Пустой объект и служебные поля (`id`, `createdAt`, `updatedAt`, `availableCopies`) отклоняются с 400. Правила значений и нормализация ISBN совпадают с POST. Поля `publicationYear` и `genre` в PATCH можно очистить явным `null`; остальные поля `null` не принимают. При успехе обновляется `updatedAt` и возвращается актуальный `availableCopies`.

Проверка количества и обновление выполняются в одной транзакции на одном соединении с `SELECT ... FOR UPDATE` строки книги. Количество невозвращённых выдач считается SQL-запросом по `returned_at IS NULL`. При трёх невозвращённых выдачах `totalCopies=3` допустимо, `totalCopies=2` — нет. Ошибка откатывает транзакцию; соединение освобождается в `finally`. Выдача использует ту же блокировку строки книги.

DELETE разрешён только при полном отсутствии истории выдач. Любая выдача, в том числе возвращённая, запрещает удаление. Связанные выдачи не удаляются. Внешний ключ `ON DELETE RESTRICT` дополнительно защищает от выдачи, появившейся между проверкой и удалением; такая ошибка PostgreSQL преобразуется в HTTP 409.

| HTTP | Код | Значение |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Некорректный ID, поля или пустой PATCH |
| 404 | `BOOK_NOT_FOUND` | Книга отсутствует |
| 409 | `BOOK_ALREADY_EXISTS` | ISBN занят другой книгой |
| 409 | `INSUFFICIENT_TOTAL_COPIES` | Количество экземпляров не может быть меньше числа невозвращённых выдач |
| 409 | `BOOK_HAS_LOANS` | Невозможно удалить книгу, имеющую историю выдач |

## API читателей

| Метод и путь | Результат |
| --- | --- |
| `POST /api/readers` | Регистрация, HTTP 201, статус `active` |
| `GET /api/readers` | Список с поиском, статусом и пагинацией |
| `GET /api/readers/:id` | Карточка без истории выдач |
| `PATCH /api/readers/:id` | Редактирование данных, блокировка или разблокировка, HTTP 200 |

Примеры запросов (Bash):

```sh
curl -X POST http://localhost:3000/api/readers \
  -H 'Content-Type: application/json' \
  -d '{"fullName":"Иванов Иван Иванович","email":"ivanov@example.com","registrationNumber":"LIB-000001"}'
curl --get http://localhost:3000/api/readers \
  --data-urlencode 'search=Иванов' --data-urlencode 'status=active' \
  --data-urlencode 'page=1' --data-urlencode 'limit=10'
curl http://localhost:3000/api/readers/1
curl -X PATCH http://localhost:3000/api/readers/1 \
  -H 'Content-Type: application/json' \
  -d '{"fullName":"Иванов Иван Петрович","email":"ivan.petrov@example.com"}'
curl -X PATCH http://localhost:3000/api/readers/1 \
  -H 'Content-Type: application/json' -d '{"status":"blocked"}'
curl -X PATCH http://localhost:3000/api/readers/1 \
  -H 'Content-Type: application/json' -d '{"status":"active"}'
```

При регистрации обязательны непустые `fullName`, `registrationNumber` и корректный `email`. Пробелы по краям удаляются, email сохраняется в нижнем регистре. Статус `active` и временные метки устанавливает БД; клиенту запрещено задавать `status`, `id`, `createdAt`, `updatedAt` при POST. Уникальность email без учёта регистра и регистрационного номера обеспечивается существующими индексами PostgreSQL, в том числе при конкурентных запросах.

PATCH разрешает только `fullName`, `email`, `registrationNumber`, `status`. Отсутствующие поля сохраняются, пустой объект, неизвестные поля и `null` отклоняются. Обновление выполняется одним атомарным UPDATE с `RETURNING`, меняет `updatedAt` и при конфликте не сохраняет ни одно поле запроса.

`search` ищет подстроку в ФИО, email или регистрационном номере без учёта регистра. `status` принимает только `active`/`blocked`. Поиск и фильтр можно совмещать. `page=1`, `limit=10` по умолчанию, максимум `limit=100`; сортировка `id ASC`, формат ответа `data/pagination` совпадает с каталогом книг. Фильтрация, подсчёт и LIMIT/OFFSET выполняются в PostgreSQL. Для ID и пагинации книги и читатели используют общие схемы из `src/schemas/common.schemas.js`.

Блокировка сохраняет читателя и не меняет его выдачи. Заблокированный читатель доступен через GET и фильтр `status=blocked`. Повторное выставление текущего статуса разрешено. Новая выдача заблокированному читателю запрещена. DELETE читателей и отдельные `/block`/`unblock` отсутствуют.

| HTTP | Код | Значение |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Неверные поля, ID, query, статус или пустой PATCH |
| 404 | `READER_NOT_FOUND` | Читатель отсутствует |
| 409 | `EMAIL_ALREADY_EXISTS` | Email занят другим читателем |
| 409 | `REGISTRATION_NUMBER_ALREADY_EXISTS` | Регистрационный номер занят другим читателем |

## Выдача книг

`POST /api/loans` выдаёт книгу активному читателю, если существует свободный экземпляр:

```sh
curl -X POST http://localhost:3000/api/loans \
  -H 'Content-Type: application/json' \
  -d '{"bookId":1,"readerId":2}'
```

Тело принимает только `bookId` и `readerId` — положительные целые JSON-числа. Все дополнительные поля, включая `status`, `dueDate`, `loanedAt`, `fineAmount`, запрещены. Успешный ответ — HTTP 201 с `id`, `bookId`, `readerId`, `loanedAt`, `dueDate`, `returnedAt`, `status`, `fineAmount`, `createdAt`. Начальные значения: `status: "active"`, `returnedAt: null`, `fineAmount: "0.00"`. Денежные значения выдач возвращаются десятичными строками с двумя знаками, без преобразования в JavaScript Number.

Время выдачи берётся на сервере БД после получения блокировок. Плановая дата — календарная дата этого времени в UTC плюс 14 дней; она возвращается строкой `YYYY-MM-DD`, независимо от часового пояса соединения PostgreSQL или Node.js. Клиент не задаёт срок возврата. В SQL используется одна временная метка для `loanedAt` и вычисления `dueDate`.

Операция целиком выполняется на одном `client` в транзакции: книга блокируется `SELECT ... FOR UPDATE`, читатель — `FOR SHARE`, затем SQL считает выдачи с `returned_at IS NULL` и создаёт запись. При ошибке — ROLLBACK, при успехе — COMMIT; соединение освобождается в `finally`. Блокировка строки книги сериализует проверку остатка и INSERT: два конкурентных запроса последнего экземпляра получают один 201 и один 409. Ту же блокировку использует PATCH количества экземпляров. Блокировка читателя защищает проверку его статуса от конкурентного изменения до завершения выдачи.

`availableCopies` в обоих GET книг автоматически уменьшается благодаря существующему SQL-расчёту. Учитываются все невозвращённые выдачи, включая `overdue`; отдельная колонка остатка не создаётся. Конкурентные тесты используют настоящие соединения и блокировки PostgreSQL; ожидание контролируется через `pg_blocking_pids`, без предположений о времени выполнения запросов. Проверяется также откат INSERT при ошибке COMMIT.

| HTTP | Код | Значение |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Некорректные, отсутствующие ID или запрещённые поля |
| 404 | `BOOK_NOT_FOUND` | Книга не найдена |
| 404 | `READER_NOT_FOUND` | Читатель не найден |
| 409 | `READER_BLOCKED` | Выдача книг заблокированному читателю запрещена |
| 409 | `BOOK_UNAVAILABLE` | Нет доступных экземпляров книги |

Продление срока пока не реализовано.

### Просмотр выдач и истории операций

| Метод и путь | Результат |
| --- | --- |
| `GET /api/loans` | Список выдач и история операций с фильтрами и пагинацией |
| `GET /api/loans/:id` | Выдача по ID, HTTP 200; отсутствующая — 404 `LOAN_NOT_FOUND` |

Параметры списка можно сочетать:

| Query-параметр | Значение |
| --- | --- |
| `readerId` | Положительный целый ID читателя; позволяет получить его историю |
| `bookId` | Положительный целый ID книги |
| `status` | `active`, `overdue` или `returned` |
| `page` | Положительный целый номер страницы, по умолчанию 1 |
| `limit` | Число записей от 1 до 100, по умолчанию 10 |

```sh
curl 'http://localhost:3000/api/loans?readerId=2&bookId=1&status=returned&page=1&limit=5'
curl http://localhost:3000/api/loans/1
```

Пример ответа списка HTTP 200:

```json
{
  "data": [
    {
      "id": 1,
      "bookId": 1,
      "readerId": 2,
      "loanedAt": "2026-11-01T10:00:00.000Z",
      "dueDate": "2026-11-15",
      "returnedAt": null,
      "status": "active",
      "fineAmount": "0.00",
      "createdAt": "2026-11-01T10:00:00.000Z"
    }
  ],
  "pagination": { "page": 1, "limit": 10, "total": 1, "totalPages": 1 }
}
```

Отдельная выдача возвращается в том же формате, без оболочки `data` и `pagination`. Денежные суммы остаются строками с двумя десятичными знаками; `dueDate` — календарной датой `YYYY-MM-DD`, временные метки — ISO 8601 в UTC, `returnedAt` до возврата равен `null`.

Фильтры применяются совместно через AND. PostgreSQL считает `total` с учётом фильтров, сортирует по `id ASC` и выбирает страницу через LIMIT/OFFSET. Если совпадений нет или страница выходит за пределы списка, возвращаются HTTP 200 и `data: []`. Для отсутствующих совпадений `total` и `totalPages` равны 0; корректный ID книги или читателя без выдач не вызывает 404.

Статусы: `active` — активная выдача, `overdue` — отмеченная просрочка, `returned` — завершённая выдача. GET возвращает статус, сохранённый в PostgreSQL, и ничего не изменяет: до ближайшей фоновой или ручной проверки выдача с истёкшим сроком может оставаться `active`.

Ошибки просмотра: HTTP 400 `VALIDATION_ERROR` при неверном ID, статусе, параметрах пагинации или неизвестном query-параметре; HTTP 404 `LOAN_NOT_FOUND` для отсутствующей выдачи по ID; HTTP 500 `INTERNAL_SERVER_ERROR` без внутренних сведений при непредвиденной ошибке. Используется общий формат `error`.

Шесть целевых тестов просмотра в `tests/loans.test.js` проверяют список, совместные фильтры, сохранённые статусы, пагинацию, отдельную выдачу и ошибки. Запуск: `npm test -- tests/loans.test.js` с отдельной `TEST_DATABASE_URL`.

### Возврат книги и штраф

`POST /api/loans/:id/return` возвращает книгу. Тело не требуется; допускается `{}`. Другие поля, в том числе дата возврата, статус и штраф, отклоняются с HTTP 400.

```sh
curl -X POST http://localhost:3000/api/loans/1/return
```

Пример ответа HTTP 200 (просрочка на два дня при ставке 10):

```json
{
  "id": 1,
  "bookId": 1,
  "readerId": 2,
  "loanedAt": "2026-11-01T10:00:00.000Z",
  "dueDate": "2026-11-10",
  "returnedAt": "2026-11-12T10:00:00.000Z",
  "status": "returned",
  "fineAmount": "20.00",
  "createdAt": "2026-11-01T10:00:00.000Z"
}
```

Возврат разрешён для невозвращённых выдач `active` и `overdue`, в том числе заблокированному читателю. Факт возврата определяется по `returned_at`, независимо от статуса и запуска cron. После возврата `availableCopies` автоматически увеличивается; `totalCopies` не изменяется, история выдачи сохраняется.

Ставка `FINE_PER_DAY` по умолчанию — `10`. Допускается неотрицательное десятичное число с точкой, например `2.555` или `0`. Пустая строка, отрицательные значения, `NaN`, `Infinity`, запятая и экспоненциальная запись отклоняются; некорректная конфигурация не позволяет запустить HTTP-сервер. Ставка хранится и передаётся в SQL строкой, без JavaScript Number. Compose передаёт её в контейнер API из окружения или `.env`.

Формула: `max(0, дата_возврата_UTC - dueDate) × FINE_PER_DAY`. Вся арифметика выполняется PostgreSQL NUMERIC с округлением итоговой суммы до двух знаков. В день срока и раньше штраф равен `"0.00"`; через два календарных дня при ставке 10 — `"20.00"`. Ставка `2.555` за три дня даёт `"7.67"`. Время возврата и его UTC-дата берутся из одной временной метки PostgreSQL, независимо от часового пояса соединения.

Транзакция сначала находит связанную книгу, блокирует её `FOR UPDATE`, затем блокирует выдачу `FOR UPDATE`. Проверка `returned_at` и UPDATE выполняются на одном соединении; ошибка вызывает ROLLBACK, соединение освобождается в `finally`. Порядок блокировок совместим с выдачей и PATCH книги. Из двух одновременных возвратов успешен один, второй получает 409; уже зафиксированные время и штраф не перезаписываются.

| HTTP | Код | Значение |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Неверный ID или запрещённые поля тела |
| 404 | `LOAN_NOT_FOUND` | Выдача не найдена |
| 409 | `LOAN_ALREADY_RETURNED` | Книга уже возвращена |

Тесты текущего модуля: `npm test -- tests/loans.test.js` с указанной выше `TEST_DATABASE_URL`. Для возврата добавлены семь основных проверок: вовремя, просрочка, повтор, отсутствие выдачи, восстановление остатка, конкурентный возврат и изменённая ставка.

## Автоматическая проверка просрочек

`node-cron` запускает проверку ежедневно в **00:05 UTC**: `CRON_SCHEDULE="5 0 * * *"`. Часовой пояс явно задан как UTC и не зависит от часового пояса Windows, Node.js или сеанса PostgreSQL. В Compose расписание передаётся в существующий контейнер API; отдельного контейнера cron нет.

Планировщик создаётся только в `src/server.js`, не при импорте `src/app.js`. При `NODE_ENV=test` он отключён. Параметр `noOverlap` запрещает перекрывающиеся плановые запуски одной задачи внутри процесса. Обработчик пишет количество обновлений или краткую ошибку в консоль; сбой не останавливает сервер и не отменяет следующие запуски. При SIGINT/SIGTERM сервер уничтожает задачу, завершает HTTP-запросы и закрывает пул PostgreSQL.

Cron и ручной скрипт вызывают одну функцию `checkOverdueLoans` сервиса выдач. Репозиторий выполняет один параметризованный UPDATE: меняет `active` на `overdue`, только если `returned_at IS NULL` и `due_date < (CURRENT_TIMESTAMP AT TIME ZONE 'UTC')::date`. Он возвращает число обновлённых строк без загрузки выдач в JavaScript. Срок сегодня и будущие даты не считаются просрочкой. Возвращённые и уже просроченные выдачи не меняются; повторная проверка без новых просрочек возвращает 0.

Проверка меняет только статус. Даты выдачи и возврата, книги, читатели и штрафы сохраняются. Окончательный штраф рассчитывается исключительно при фактическом возврате по прежним правилам, даже если cron ещё не успел отметить просрочку.

Ручной запуск с локальной `DATABASE_URL`:

```sh
npm run loans:check-overdue
```

Совместимый псевдоним — `npm run overdue:check`. Скрипт выводит число обновлений, закрывает пул и при ошибке завершается с ненулевым кодом. Он не запускает HTTP-сервер и планировщик. Через Docker:

```sh
docker compose exec api npm run loans:check-overdue
docker compose logs --tail 30 api
```

### Демонстрация на защите

1. Выполните `docker compose up --build -d`, проверьте `/api/health`. В логах API появится расписание `5 0 * * * (UTC)`.
2. Через POST `/api/books`, `/api/readers`, `/api/loans` создайте отдельную временную книгу, читателя и выдачу (примеры выше). Запишите их ID. Далее замените `<LOAN_ID>`, `<BOOK_ID>` и `<READER_ID>` фактическими числами только этих временных записей.
3. Подготовьте трёхдневную просрочку исключительно для созданной выдачи:

```sh
docker compose exec db psql -U web_maga -d web_maga -c "UPDATE loans SET due_date = (CURRENT_TIMESTAMP AT TIME ZONE 'UTC')::date - 3 WHERE id = <LOAN_ID>;"
```

4. Запустите `docker compose exec api npm run loans:check-overdue`. Без других новых просрочек результат — 1. GET `/api/loans/<LOAN_ID>` покажет `overdue`, `returnedAt: null`, `fineAmount: "0.00"`.
5. Повторите команду: результат — 0, запись не изменится. Так демонстрируется та же бизнес-функция без ожидания 00:05 UTC.
6. Выполните POST `/api/loans/<LOAN_ID>/return`: статус станет `returned`, штраф при ставке 10 — `"30.00"`, если возврат происходит в тот же день UTC. GET подтвердит сохранённые значения.
7. Удалите только созданные временные записи, сохранив остальные данные и Docker volume:

```sh
docker compose exec db psql -U web_maga -d web_maga -v ON_ERROR_STOP=1 -c "BEGIN; DELETE FROM loans WHERE id = <LOAN_ID> AND book_id = <BOOK_ID> AND reader_id = <READER_ID>; DELETE FROM books WHERE id = <BOOK_ID>; DELETE FROM readers WHERE id = <READER_ID>; COMMIT;"
```

При изменённых `POSTGRES_USER`/`POSTGRES_DB` используйте свои значения вместо демонстрационных. Пять тестов функции проверки находятся в `tests/loans.test.js`: прошедший срок, сегодня/будущее, возвращённые, уже просроченные и повторный запуск. Команда `npm test -- tests/loans.test.js` с отдельной `TEST_DATABASE_URL` проверяет их напрямую, не ожидая cron.

## Проверка состояния

`GET /api/health` выполняет `SELECT 1` через пул соединений:

- Доступная БД: HTTP 200, `{"status":"ok","database":"connected"}`.
- Недоступная БД: HTTP 503, `{"status":"error","database":"disconnected"}`.

Ответ не содержит строку подключения и внутренние ошибки БД.

Воспроизводимая проверка отключения БД и восстановления:

```sh
docker compose stop db
curl -i http://localhost:3000/api/health
docker compose start db
curl -i http://localhost:3000/api/health
docker compose up --build -d
```

После `start db` дождитесь готовности БД (`docker compose ps`), затем проверьте HTTP 200. Проверка синтаксиса: `node --check src/app.js`, `node --check src/server.js`, `node --check src/db/pool.js`.
