# Library Management API

Учебный REST API для управления библиотечным фондом по `LIBRARY_MANAGEMENT_SPEC.md`.
Выполнены этапы 1–3: каркас, SQLite, миграции, CRUD книг и читателей,
поиск, фильтры, пагинация, выдача и возврат книг с транзакциями и валидацией.
Расчёт штрафов и ежедневная проверка просрочек относятся к следующему этапу 4.

## Требования и установка

Node.js **24 LTS** и npm. JavaScript ES Modules, Express, `better-sqlite3` и Zod.
Загрузка `.env`, режим наблюдения и проверки используют встроенные средства Node.js.

Для получения проекта и установки точных версий из `package-lock.json`:

```sh
git clone https://github.com/Lirkul/Web-MAGA.git
cd Web-MAGA
npm ci
```

Если проект уже открыт локально, выполните только `npm ci` в его корне.
`better-sqlite3` закреплён на версии `12.11.1`: чистая установка и работа
готового модуля проверены на Windows x64 с Node.js 24. Отдельный сервер SQLite,
Python и инструменты компиляции для проверенного окружения не требуются.

Скопируйте `.env.example` в `.env`, если локального `.env` ещё нет:

```powershell
Copy-Item .env.example .env
```

Linux/macOS: `cp .env.example .env`. В PowerShell при блокировке `npm.ps1`
используйте `npm.cmd` вместо `npm`; менять Execution Policy не требуется.

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | Порт HTTP-сервера |
| `DATABASE_PATH` | `./data/library.sqlite` | Файл постоянной SQLite-базы |
| `DAILY_FINE_KOPECKS` | `1000` | Будущий тариф штрафа в копейках за день |
| `MAX_ACTIVE_LOANS` | `5` | Лимит невозвращённых выдач на читателя |
| `DEFAULT_LOAN_DAYS` | `14` | Срок выдачи по умолчанию в календарных днях UTC |

`.env` загружается автоматически. Уже заданные переменные окружения имеют приоритет.
Относительный путь базы отсчитывается от корня проекта; каталог создаётся автоматически.
Без `.env` действуют значения по умолчанию. Числовые настройки проверяются при запуске.
Файл `.env`, зависимости и локальная база исключены из Git.

## Запуск и проверка

```sh
npm run db:migrate
npm run dev
```

Для обычного запуска: `npm start`. `dev` перезапускает сервер при изменениях файлов.
При запуске сервера миграции также выполняются автоматически, до открытия порта.
Повторное применение миграций безопасно: имена выполненных файлов записываются
в `schema_migrations`; каждая миграция выполняется в транзакции.

В другом терминале:

```sh
curl http://localhost:3000/api/health
```

Ожидается HTTP `200` и `{"status":"ok"}`. В Windows можно использовать `curl.exe`
или `Invoke-RestMethod http://localhost:3000/api/health`.
Health проверяет работу HTTP-сервера; подключение и миграции БД проверяются при старте.
Остановка: `Ctrl+C`, после завершения HTTP-запросов соединение с БД закрывается.

```sh
npm test
```

42 проверки этапов 1–3 используют отдельные временные файлы SQLite, не базу разработки:
миграции, сохранение данных, ограничения схемы, CRUD через HTTP, нормализация,
уникальность, кириллица в поиске, пагинация, защита истории выдач и обработка ошибок;
также выдача и возврат, даты UTC, лимиты и одновременные операции через отдельные
подключения к SQLite. Часы и настройки можно передать в `createApp(database, options)`
для тестов; служебного HTTP-маршрута для изменения времени или настроек нет.

## API этапа 2

| Метод | Маршрут | Результат |
|---|---|---|
| `GET` | `/api/books` | Список книг с поиском и фильтрами |
| `GET` | `/api/books/:id` | Книга по ID |
| `POST` | `/api/books` | Создание книги |
| `PATCH` | `/api/books/:id` | Частичное изменение, включая архивирование |
| `DELETE` | `/api/books/:id` | Удаление книги без истории выдач |
| `GET` | `/api/readers` | Список читателей с поиском и фильтром статуса |
| `GET` | `/api/readers/:id` | Читатель по ID |
| `POST` | `/api/readers` | Создание читателя |
| `PATCH` | `/api/readers/:id` | Частичное изменение, включая блокировку |
| `DELETE` | `/api/readers/:id` | Удаление читателя без истории выдач |
| `GET` | `/api/readers/:id/loans` | Чтение истории выдач читателя |

Для списков и истории доступны `page` (по умолчанию 1), `limit` (по умолчанию 20,
максимум 100). Формат ответа: `{ "page": 1, "limit": 20, "total": 0, "items": [] }`.
`total` учитывает фильтры, но не ограничение страницы. Для страницы за пределами списка
возвращается пустой `items` с исходным `total`.

Книги: `q` — подстрока названия или ISBN, `genre` — точный жанр,
`author` — подстрока имени любого автора, `availableOnly=true` — только неархивные
книги с доступными экземплярами. `availableOnly=false` не ограничивает выборку.
Поиск и жанр не зависят от регистра, включая кириллицу. Фильтры можно комбинировать.
ISBN в поисковом запросе также может содержать пробелы и дефисы.

Читатели: `q` ищет подстроку ФИО, email или регистрационного номера,
`status` принимает `ACTIVE` или `BLOCKED`. Поиск не зависит от регистра.
Книги сортируются по названию без учёта регистра, затем по ID; читатели — по ФИО,
затем по ID. История сортируется по `loanedAt` и ID по убыванию.

`POST` возвращает `201` и заголовок `Location`, чтение и `PATCH` — `200`,
успешное удаление — `204` без тела. Неизвестный ID даёт `404`.
Неверное тело, ID, параметры, неизвестные поля и пустой `PATCH` дают `400`.
Ошибки имеют вид `{ "error": { "code": "...", "message": "...", "details": {} } }`;
при ошибке валидации `details.issues` содержит пути полей и причины.
Повторяющиеся query-параметры не принимаются. Строки не преобразуются в числа и boolean
в JSON-теле; числовые ID и параметры страниц передаются строками в URL.

ISBN очищается от пробелов и дефисов, `x` преобразуется в `X`.
Email обрезается по краям и сохраняется в нижнем регистре. Остальные текстовые поля
обрезаются по краям. ID, временные метки и `availableCopies` менять через API нельзя.
Если ISBN, email или регистрационный номер уже заняты, возвращается `409`.
Уменьшение числа экземпляров ниже невозвращённых также даёт `409`.
Удаление при наличии любой истории выдач, включая возвращённые, запрещено с `409`:
нужно архивировать книгу (`isArchived: true`) или блокировать читателя (`status: "BLOCKED"`).

Пример в PowerShell (после запуска сервера):

```powershell
$body = @{
  title = 'Преступление и наказание'
  authors = @('Фёдор Достоевский')
  isbn = '978-5-17090630-4'
  publishedYear = 1866
  genre = 'Роман'
  totalCopies = 4
} | ConvertTo-Json
$book = Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/books -ContentType 'application/json; charset=utf-8' -Body $body
Invoke-RestMethod "http://localhost:3000/api/books/$($book.id)"
Invoke-RestMethod 'http://localhost:3000/api/books?page=1&limit=10&availableOnly=true'
Invoke-RestMethod -Method Patch -Uri "http://localhost:3000/api/books/$($book.id)" -ContentType 'application/json' -Body '{"isArchived":true}'
Invoke-RestMethod -Method Delete -Uri "http://localhost:3000/api/books/$($book.id)"
```

Для `POST /api/readers` обязательны `fullName`, `email`, `registrationNumber`;
статус по умолчанию `ACTIVE`. В `PATCH` обоих ресурсов передаются только изменяемые поля.

## API этапа 3

| Метод | Маршрут | Результат |
|---|---|---|
| `GET` | `/api/loans` | Список выдач с фильтрами и пагинацией |
| `GET` | `/api/loans/:id` | Выдача по ID |
| `POST` | `/api/loans` | Выдача книги, HTTP `201` и заголовок `Location` |
| `POST` | `/api/loans/:id/return` | Возврат книги, HTTP `200` |

Список поддерживает `status` (`ACTIVE`, `OVERDUE`, `RETURNED`), `bookId`, `readerId`,
`page`, `limit`. Фильтры комбинируются; формат страницы такой же, как у книг.
Сортировка — по `loanedAt`, затем ID по убыванию. Редактирования и удаления выдач нет.

Тело выдачи: `{ "bookId": 1, "readerId": 2 }`, необязательно `dueDate` в формате
`YYYY-MM-DD`. Если срок не задан, к календарной дате выдачи UTC прибавляется
`DEFAULT_LOAN_DAYS` (по умолчанию 14). Явная дата должна существовать в календаре
и быть позднее текущей даты UTC. Срок включает весь указанный день UTC.
Клиент не может задавать статус, время выдачи/возврата или сумму штрафа.

Выдача разрешена, когда книга существует, не архивирована и имеет свободный экземпляр;
читатель существует, активен, не имеет текущих просрочек и не достиг `MAX_ACTIVE_LOANS`.
В лимит входят `ACTIVE` и `OVERDUE`, возвращённые записи не учитываются.
Просрочка проверяется по `dueDate < today` среди невозвращённых выдач,
даже если статус записи ещё `ACTIVE`. В день `dueDate` выдача не считается просроченной.
Все проверки и создание выполняются в одной транзакции `IMMEDIATE`, поэтому
два подключения не могут одновременно выдать последнюю копию или превысить лимит.

Возврат принимает пустое тело или `{}`. Он устанавливает `RETURNED` и `returnedAt`
в UTC в одной транзакции. Заблокированный читатель может вернуть книгу;
архивирование книги после выдачи тоже не препятствует возврату.
`totalCopies` при выдаче и возврате не меняется. `availableCopies` пересчитывается
SQL-запросом по незакрытым выдачам. Изменения сразу видны в карточке книги,
фильтре `availableOnly` и истории читателя.

Неизвестная книга, читатель или выдача дают `404`. Отсутствие копий, архивная книга,
блокировка, текущая просрочка, превышение лимита и повторный возврат дают `409`
с понятным `error.code`. Неверные поля, даты и параметры дают `400`.

Пример полного цикла в PowerShell (используйте уникальные ISBN, email и номер):

```powershell
$bookBody = @{
  title = 'Книга для выдачи'; authors = @('Автор'); isbn = '9785000000009'
  publishedYear = 2020; genre = 'Наука'; totalCopies = 1
} | ConvertTo-Json
$book = Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/books -ContentType 'application/json; charset=utf-8' -Body $bookBody
$readerBody = @{
  fullName = 'Иван Иванов'; email = 'ivan@example.com'; registrationNumber = 'R-DEMO-1'
} | ConvertTo-Json
$reader = Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/readers -ContentType 'application/json; charset=utf-8' -Body $readerBody
$loanBody = @{ bookId = $book.id; readerId = $reader.id } | ConvertTo-Json
$loan = Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/loans -ContentType 'application/json' -Body $loanBody
Invoke-RestMethod "http://localhost:3000/api/books/$($book.id)" # availableCopies = 0
Invoke-RestMethod -Method Post -Uri "http://localhost:3000/api/loans/$($loan.id)/return"
Invoke-RestMethod "http://localhost:3000/api/books/$($book.id)" # availableCopies = 1
Invoke-RestMethod "http://localhost:3000/api/readers/$($reader.id)/loans"
```

Ограничение этапа 3: новые выдачи имеют `fineAmount = 0`; возврат сохраняет уже
записанную сумму. Окончательный расчёт штрафа при возврате и автоматический перевод
`ACTIVE` в `OVERDUE` ещё не выполняются: они добавляются вместе с cron в этапе 4.

## Структура и схема

```text
src/
  app.js                         Express и middleware, без открытия порта
  server.js                      SQLite, миграции, запуск и остановка HTTP
  config/index.js                .env и единая конфигурация
  routes/health.routes.js         HTTP GET /api/health
  routes/books.routes.js          HTTP книг
  routes/readers.routes.js        HTTP читателей
  routes/loans.routes.js          HTTP выдачи и возврата
  middleware/error-handler.js    JSON-ошибки без стеков в ответах
  middleware/validate.js          проверка тела, URL и query через Zod
  schemas/                       схемы книг, читателей и пагинации
  services/                      правила CRUD, выдачи и возврата
  repositories/                  параметризованные SQL-запросы книг, читателей и выдач
  utils/errors.js                HTTP-ошибки с кодом и сообщением
  utils/dates.js                 календарные даты и прибавление дней UTC
  db/database.js                 подключение better-sqlite3, foreign_keys=ON
  db/migrate.js                  применение SQL-миграций
  db/run-migrations.js           точка входа команды db:migrate
  db/migrations/001_initial.sql   таблицы, индексы и ограничения
tests/
  infrastructure.test.js         проверки каркаса и БД
  catalog.test.js                HTTP-тесты этапа 2
  loans.test.js                  HTTP и конкурентные проверки этапа 3
  support/api-fixture.js         общие временная БД и HTTP-клиент тестов
  support/loans-worker.js        отдельное подключение для одновременных операций
```

Маршруты отвечают за HTTP, `schemas` — за входные данные, `services` — за бизнес-правила,
`repositories` — за SQL и преобразование JSON/boolean из SQLite.
Слой `db` управляет соединением и схемой. `createApp(database)` получает готовое соединение:
импорт `app.js` не открывает порт и не создаёт базу. Тесты передают свою временную БД.
Проверки и изменения при редактировании/удалении, выдаче и возврате объединены транзакцией `IMMEDIATE`,
чтобы параллельные записи не нарушили ограничения. SQL-значения передаются параметрами.

Схема содержит все поля `books`, `readers`, `loans` из раздела 3 ТЗ.
Имена столбцов соответствуют camelCase ТЗ. Автоматические целочисленные PK,
`NOT NULL`, `UNIQUE`, `CHECK` и строгие типы SQLite защищают основные инварианты.
Авторы хранятся JSON-массивом непустых строк в `TEXT`, ISBN — в нормализованной форме.
Email уникален с `COLLATE NOCASE` (регистронезависимость ASCII в SQLite);
Zod проверяет и нормализует входные данные до записи.
Для поиска по кириллице каждое подключение регистрирует SQL-функцию `lower_unicode`,
использующую `String.toLowerCase()`. Поиск подстрок выполняет SQL `instr`, поэтому
`%`, `_` и кавычки в запросе рассматриваются как обычные символы.
Триггеры проверяют динамическую верхнюю границу года издания и обновляют `updatedAt`.
Время создания хранится в UTC с суффиксом `Z`; `dueDate` — календарная дата `YYYY-MM-DD`.
Статус возврата согласован с наличием `returnedAt`, штраф — неотрицательное целое.
Внешние ключи запрещают удаление книг и читателей с любыми связанными выдачами.
Созданы четыре индекса выдач, рекомендованные ТЗ; уникальные поля индексирует SQLite.
`availableCopies` отдельно не хранится: SQL вычисляет его по `ACTIVE` и `OVERDUE`.
Это чтение используется для карточки, фильтра `availableOnly`, проверки редактирования
фонда и доступности при выдаче. История читателя включает созданные и возвращённые выдачи.

## Границы этапа 3

Работают `/api/health`, CRUD книг и читателей, выдача и возврат, списки и история выдач.
Неизвестные маршруты возвращают JSON с HTTP `404`, неверные ID известных ресурсов — `400`.
Расчёт штрафов, cron, статистика, CSV-импорт, Swagger и demo seed будут добавляться
по отдельным запросам на этапы 4–7. Просроченные и исторические записи для тестов
создаются SQL-фикстурами; обычный цикл выдачи и возврата проверяется через API.
Структура БД этапа 1 не менялась; существующие локальные данные сохраняются.
